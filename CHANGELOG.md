# Changelog

## Unreleased

- **Fixed: `Stow.awsSdkV3Config` silently discarded the caller's `forcePathStyle`.** The function spread the caller's options and then set `forcePathStyle: true` over the top, so a caller asking for virtual-hosted addressing received a path-style config and a 404 from a provider that never saw the request arrive in the form it was sent. `forcePathStyle` is declared in the public `AwsSdkV3ConfigOptions` type and `buildAwsSdkV3Config` honors it, so the option looked like it worked at every layer except the one that discarded it — and the existing test asserted the discarded value, pinning the defect rather than the intent. A declared option that cannot be set is worse than an absent one, because the type says it works.

  Omitting the option still yields path-style, so nothing changes for a caller who was not asking for anything else. The `StowInstance` arm keeps a fixed `true`: an instance is stow's own loopback server with a generated bucket, and `StowInstance` carries no addressing field to forward.

- **Corrected three references to tests that no longer exist under those names.** `cmd/stow-s3/store.go` pointed at `TestLocalModeBuildsNoUpstreamPath`, and `docs/adr/0005-live-write-requires-explicit-consent.md` and `docs/agentic-dx-10-plan.md` both pointed at `TestLocalModeMakesZeroUpstreamRequests`. The tests were renamed during the agent-DX safety work and the pointers were not followed. All three now name the current tests, whose behavior matches what the citing text already described. Only the identifiers changed; no decision, claim, or reasoning was edited. The matching entries in `CLIPBOARD.md` are left alone, because they record what a test was called when a past measurement was taken.

- **Added: upstream bucket addressing is configurable, after being hard-coded to path-style.** The run-through client was built with `UsePathStyle: true` unconditionally, so a provider that serves only virtual-hosted addressing could not be reached at all. The failure was a DNS lookup for `bucket.endpoint.example` with nothing in stow's output to explain it, and the only workaround was an endpoint that happened to answer both ways. `STOW_UPSTREAM_ADDRESSING=path|virtual-hosted` now selects the style, and `UpstreamConfig` carries it as a field.

  Path-style stays the default. It is what every S3-compatible endpoint accepts, what the local server and both AWS SDKs use by default, and the only style that works with a bucket name containing characters a hostname cannot carry. The zero `UpstreamConfig` is path-style, so every existing construction site keeps the behavior it had; a test asserts that against the request the client actually sends rather than against the field, because the field is the thing under test.

  An unrecognized value is refused at startup, the same as `STOW_POLICY`. Defaulting it would mean a misspelling silently became path-style and sent every request to a host the provider does not answer, which is the failure mode ADR 0011 removed from mode selection: the configuration is accepted and the operator finds out from a DNS error.

  Addressing names *how* to reach a bucket, not *whether* to use an upstream, so setting it alone never selects one. That is asserted with the upstream environment explicitly cleared rather than assumed empty, since a developer shell or CI runner exports these variables for unrelated tools and a test that passes only when they happen to be unset is reporting what the machine was doing.

  One constraint is worth knowing rather than discovering: virtual-hosted addressing needs a resolvable hostname. Given a bare IP address as the endpoint, the AWS SDK keeps the bucket in the path, because a bucket name cannot be prefixed onto an IP. The wire tests use a `*.localhost` endpoint for this reason — against a `127.0.0.1` stub the SDK ignores the addressing style, so a virtual-hosted test passes for the wrong reason.

- **Fixed: a range read of a checksummed object was refused by the official AWS SDK for JavaScript.** `serveRange` emitted the object's `x-amz-checksum-*` header next to a partial body. The header describes the whole object and the body is a fragment of it, so the two cannot agree, and `@aws-sdk/client-s3` hashes what it received, finds a mismatch, and fails the call. A caller doing the ordinary thing — reading a byte range out of an object it had just written with a checksum — got a `ChecksumMismatch` error from a server that was answering correctly. The Go SDK did not surface it, which is why the wire tests and the Go corpus runner were both green while the TypeScript corpus runner was not: this was reachable only through the JavaScript client.

  The 206 now carries the representation headers without the whole-object checksum. `Content-Type`, `ETag`, `Last-Modified` and user metadata still describe the object and are still sent, because a client ranging over an object needs its ETag. Only the checksum is withheld, and it is withheld rather than recomputed: a checksum over the fragment is not the object's checksum, and for a multipart-style checksum the whole-object value is a composite of per-part values that a range does not decompose into. This is the same reasoning `internal/s3api/validators.go` already records for a 304, which carries validators but no checksum for the same reason, and the two are now one function rather than a comment and a hope.

  Found by the shared corpus rather than by reading the code: the new `rangeGet` cases are the first corpus coverage of a range read, and `range-partial-object` failed against the real `@aws-sdk/client-s3` before this fix and passes after it. Confirmed in both directions with the binary rebuilt each time, since the corpus starts a real server process and a stale binary would have shown the fix as already present.

- **Added range reads to the shared conformance corpus, which had none.** `conformance/corpus/cases.json` held 15 cases over 7 operations with no case for a range read, so the behavior was pinned only by Go unit tests inside `internal/s3api` and never by the corpus that exists to referee SDK-observable behavior across both runners. Seven cases now cover a plain range, a suffix range, an open-ended range, an end clamped past the last byte, a whole object requested as a range, and two unsatisfiable requests. Each asserts the status, the bytes, and the whole `Content-Range` value rather than the span alone, because a server can return the right bytes for a range it mis-parsed and can report a correct span beside a body assembled from the wrong offset. The unsatisfiable cases additionally assert that the size in the `bytes star-slash <size>` refusal is the real object length, confirmed with a `HeadObject`: that number is the only thing a client can use to decide what to ask for instead, and nothing else in the corpus would have noticed it being wrong.

  The corpus validator refuses a range case that could pass without the range being honored, which is the failure mode the retired driver-facade plan measured at 0.19 for the corpus as a whole: a case that expected `200` would be satisfied by a server ignoring the header entirely.

- **Unblocked the release gate: three files had grown past the 500-line file-size ratchet without being recorded, so `make standards` failed on `main`.** `cmd/stow-s3/workspace.go` reached 534 lines, `pkg/stow/checkpoint_archive.go` 543, and `internal/storage/fs/longkeys_test.go` 626, while `scripts/baselines/file-size.json` still held zero entries. The gate failed at a clean checkout of `b012f29`, so this was an omission rather than a ratchet that had drifted: the baseline's own history shrinks honestly, 2 entries to 1 to 1 to 0, each time the oversized file it named was split. Recording the three files instead of splitting them would have grown the baseline to admit a regression, which `docs/CODE_STANDARDS.md` does not permit, so each is split along a seam that already existed.

  `checkpoint_archive.go` separates writing an archive from reading one, so export and preview stay together and import moves to `checkpoint_import.go`. `workspace.go` separates the workspace lifecycle from the archive commands, so prepare, resume, and handoff stay together and the checkpoint and transfer commands move to `workspace_archive.go`. The long-key tests separate the key-to-path layout from the mutations that prune and rewrite that layout, and the two helpers that only the delete tests used move with them. No declaration changed, no signature changed, and no test was added or removed; the tests that moved are the same tests, and the packages they cover were already exercised at the wire and in the shared corpus.

  `dist/stow-runtime.wasm` is regenerated because `cmd/stow-wasm` imports `pkg/stow`, and splitting a package changes the compiler's output ordering even when no code moves. The build is deterministic, and the previously committed artifact still rebuilds byte for byte from the previous source, so `check-generated` is reporting a real source change rather than an unreproducible binary.

- **Fixed, and it is currently inert: `runtime.Open` returned an instance whose initialization had never run.** The two public constructors had drifted. `OpenWithStore` calls `instance.initialize` after building the instance, which walks the store's buckets and reconciles committed object bytes, in-flight multipart reservations, and the open-time quota check that decides whether an over-quota store may be opened at all. `Open` built its instance and returned it without that call, so the only constructor a caller could reach without supplying a store was the one that skipped it. It is a real asymmetry and it is a landmine rather than a live defect: `normalizeOptions(options, false)` rejects every backend but memory, and `Open` builds its own `NewMemoryStore`, so the walk finds no buckets and reconciles nothing today. It becomes a quota bypass the moment `Open` can be handed a store that arrives populated — usage would start at zero against objects that already exist, which makes `MaxBytes` and `MaxObjects` unenforceable rather than merely unenforced, and the `ErrQuotaExceeded` check would never run. `Open` now initializes exactly as `OpenWithStore` does.

  There is no new test for this, deliberately. The path is unreachable today, so a test against `Open` would pass identically with and without the call, and asserting the call happened would be asserting the source text rather than the behaviour. The mechanism itself is already covered where it is reachable: `TestOpenWithStoreRejectsInvalidOptionsAndInitializesUsage` opens a store holding one seven-byte object and asserts the reconciled usage. What would make a real test possible is `Open` accepting a populatable backend, which is a product decision rather than a bug fix.

- **Breaking Go API change in 0.2.0:** `stow.MultipartStore.CreateMultipartUpload` now takes a `MultipartOptions` argument. Callers must pass the options explicitly, and custom `MultipartStore` implementations must update their method signature and preserve `ContentType` and `Metadata` through completion. This source-incompatible change is accepted in the pre-1.0 0.2.0 release; no compatibility shim is provided.

- **Fixed: a completed multipart upload lost the object properties its initiation fixed.** `CreateMultipartUpload` accepted a content type, user metadata and a checksum configuration, and then had nowhere to put them: `storage.MultipartUpload` carried the upload ID, the bucket, the key and the initiation time, and the three backends persisted exactly those four fields. Completion built the object's metadata from what it had, which was nothing, so an upload initiated with `Content-Type: application/json` and `x-amz-meta-foo: bar` published an object that read back as `application/octet-stream` with no metadata. A client had no way to tell it had been given something other than what it asked for, and no later part upload could change it back.

  The fix is a `storage.MultipartOptions` — the creation-time half of `PutOptions`, minus the two fields that describe a *write* over an object rather than the object, since S3 accepts neither `If-Match` nor `If-None-Match` at initiation and there is no object yet for them to name. It is part of the upload descriptor rather than store-private, so `GetMultipartUpload` and `ListMultipartUploads` report what an in-flight upload will publish and a caller reconciling in-flight uploads can answer without completing it. All three backends persist it: in memory on the upload, in the filesystem backend's `manifest.json`, and in the workspace backend's `upload.json` — the last two because an upload outlives the process that started it, and an in-memory-only copy would lose the properties on exactly the path a workspace exists to support.

  Completion now builds the object from the persisted state. A checksum *value* the client supplied is verified against the assembled bytes, the same check a single write gets. A checksum *algorithm* on its own is not a claim: an initiation carries no body, so `x-amz-checksum-algorithm` names the algorithm to use and comes with no value, and there is nothing at completion to check it against. Handing the declaration to the store as though it were a claim made `VerifyChecksum` — which rightly refuses an algorithm without a value — fail every completion of an upload that named one, in all three backends, with an error the S3 surface cannot map. The client saw `500 InternalError` and the SDK retried three times. The algorithm is still recorded and still reported by `GetMultipartUpload` and `ListMultipartUploads`; only the verification is skipped, because deriving a whole-object checksum for a multipart upload means computing the composite of the per-part checksums, which this does not do.

  Conformance coverage is at the wire and in the shared corpus, because the answer must not depend on which store is underneath: `TestCompletedMultipartObjectCarriesInitiationProperties` in `conformance/local_test.go` through the real AWS SDK, and the shared corpus case `multipart-two-part-lifecycle`, which now carries a content type and metadata through both the Go and the TypeScript suite. Verified red by dropping the options on the way into the store and watching both fail on `application/octet-stream`.

- **Fixed: the 5 MiB minimum part size was enforced only by the S3 layer, from a part listing the completion then ignored.** `handleCompleteMultipartUpload` called `ListParts`, built a map of part numbers to sizes, and refused a part below the minimum when it was not the highest number named in the request. Two things were wrong with that. A part missing from the listing was skipped rather than refused, so the one case that must never pass was the one the check was blind to — the same failure mode a discarded `ListParts` error produced, in the code written to fix it. And a store used directly, through the embedded API or a workspace, enforced nothing at all: a caller could complete an upload the S3 surface would have refused, and the choice of interface decided the answer.

  The rule is now `storage.ValidateMinPartSizes`, called by all three backends against the stored sizes of the exact parts being assembled, before anything is allocated. `storage.ErrEntityTooSmall` maps to S3's `EntityTooSmall`, kept distinct from `InvalidPart` because a client can fix a small part and cannot fix a missing one.

  The workspace backend also reported a completion whose ETag did not match as `ErrChecksumMismatch`, which the S3 surface does not map — so an ETag naming a part that had been replaced reached a client as `500 InternalError` for what is a malformed request, and the choice of backend decided the status code. It is now `ErrInvalidPart`, which is what the other two backends already returned. The three required sizes (1 byte + 1 byte refused, 5 MiB + 1 byte accepted, a single 1-byte part accepted) are asserted per backend in `internal/storage`, at the wire in `internal/s3api`, and end to end through the AWS SDK in `conformance`.

- **Fixed: the memory backend read, hashed and materialized the whole request body before discovering the bucket did not exist.** `MemoryStore.PutObject` read the body first because it needed the bytes to compute the ETag, and only then took the store lock to check the bucket and the preconditions. So an impossible request was fully read, hashed and copied before anyone said no, with the store's single mutex held for the duration and every other operation in the process waiting behind it. The answer is unchanged — `ErrBucketNotFound` — but nothing that cannot succeed should be read to produce it.

  The check now happens before the read, and the body is consumed outside the lock. The commit revalidates the bucket under the lock, because a bucket can be deleted in between and a bucket deleted mid-request must still produce the correct failure rather than an object in a bucket that is gone. `TestStoreRejectsAMissingBucketBeforeReadingTheBody` counts reads against the body, so a change that moved the check but still read the body would fail.

  Multipart completion had the same shape with a worse consequence: the destination was grown by appending, so assembling N bytes reallocated on the way and briefly held the old buffer and the new one while every part was still retained. Each backend now resolves and validates every part first, computes the exact total, and allocates once.

- **Fixed: a completion could exceed the session's advertised byte limit by one whole object.** The runtime reserved the bytes of an in-flight upload — every part counts against the quota — but the completion check counted the object once, where the store holds it twice: the parts being assembled from, and the buffer being assembled. A session with `max-bytes: N` could therefore hold 2N while publishing a limit of N, on the memory backend where that is real memory.

  The bounded state is now committed object bytes, plus the parts of every upload in flight, plus the buffer a completion is assembling, and the check precedes the store call so a completion that cannot fit is refused before anything is built. The accounting transitions exactly once on success — the parts' reservation is released as the object takes their place — and a refused completion releases nothing, because a refusal is not a cancellation and the upload is still holding its parts.

  This narrows what a byte budget can complete: an object needs room for itself *and* its assembly. That is the honest accounting for a store that materializes, and the alternative to publishing a limit the process does not keep. `internal/runtime/multipart_quota_test.go` covers UploadPart, replacing a part, abort, a failed completion, a successful completion, an overwrite of an existing object, and two concurrent uploads sharing one budget.

- **Fixed: a presigned URL was valid arbitrarily long before its signing time.** The presigned branch checked only the expiry, and the expiry is derived from the signing time — which is inside the URL, and therefore the client's to choose. A URL signed for a date next year expires next year, so "now is after the expiry" was false and the request authenticated. Ordinary signed requests never had that freedom, because their date is bound by the signature and stow checks it for skew in both directions; the presigned branch was the asymmetry.

  It now bounds the far edge with the verifier's configured `MaxSkew`, so both kinds of request are limited by the same allowance. The allowance comes from the verifier rather than being a constant of its own, because a branch using its own idea of the allowance is the same shape of bug one level narrower. `internal/auth/sigv4_strictness_test.go` covers the four required cases at a fixed reference time — before `requestTime − allowedSkew` refused, within the allowance accepted, the normal window accepted, past the expiry refused — plus malformed, negative and over-ceiling `X-Amz-Expires` and the ceiling itself. `conformance/local_test.go` re-asserts it at the wire with a genuine SDK signature computed at a future time, so a refusal for a mismatched signature cannot stand in for the time check.

- **Local-only is now the default; ambient credentials no longer select an upstream.** `DetectMode` returned run-through whenever the upstream environment resolved, and `UpstreamConfig.FromEnv` falls back to `AWS_*`. A developer shell or a CI runner has those exported for unrelated tools, so whether stow contacted a live provider was a property of the machine rather than of anything the user asked for. The stated mitigation — a loud banner, read-only default writes — covered writing and did nothing about reading, which is the half that is easy to trigger by accident.

  The invariant is one line: no explicit request, no upstream. `--mode run-through` or `STOW_MODE=run-through` is the request, and credentials decide how a requested upstream is *authenticated*, not whether one is used. `STOW_MODE=local` still forces local, and an unrecognized value is local rather than an error or a fallback — refusing to start would mean a typo stops a harmless dev server, and falling back to auto-detection would mean the typo re-enabled exactly what this removes. The `--mode` default moved from `auto` to empty, because an `auto` default advertises that something else can select run-through. The local-mode banner now names how to ask for it, since "the configuration was not asking" and "the credentials were absent" are indistinguishable from outside.

  ADR 0001 remains unchanged for history and is superseded in full by [ADR 0011](docs/adr/0011-local-is-the-default-mode.md), because "developers already have live vars in their environment" was the argument for the old default and is now the argument against it. The separate live-write consent requirement is unchanged and is not weakened here: `TestRunThroughWithMirrorWritesIsNotPermissionToMutateUpstream` asserts that a run-through configuration carrying `mirrorWrites` still writes locally, reports `mirrorWrites-disabled`, and produces a banner that does not warn about propagation.

- **Fixed: SigV4 `SignedHeaders` was repaired rather than refused, so a request could be authenticated against a header list the client never wrote.** The parser split on `;`, trimmed, lower-cased, dropped empty entries and sorted. Every one of those is a way to authenticate against a different set of headers than the signature covers: `host;;x-amz-date` became the same list as `host;x-amz-date`; `host; X-Amz-Date` became the same list as the lower-case spelling; `host;host` named one header twice; and sorting discarded the order the client wrote, which the canonical request embeds verbatim.

  All of them are now refused, along with the structural cases: a name that is not a valid HTTP field name, a list with no `host`, an empty list, and a list that is not ascending. A signed header sent in any case is still found — `X-Amz-Meta-Foo` on the wire against `x-amz-meta-foo` in the list — because HTTP field names are case-insensitive and SigV4 canonicalizes them, and refusing that would be a false negative against every conforming signer.

- **Fixed: a repeated `Authorization` component resolved to whichever came last.** The grammar has exactly three components and each may appear once, so a repeat is a header saying two different things rather than a variant to reconcile. Last-one-wins made the header's meaning depend on component order: a request carrying a valid `Credential` and a substituted `Signature` was read as whichever signature arrived last. `Credential`, `SignedHeaders` and `Signature` are each claimed at most once now.

  An unrecognized component is refused rather than skipped. That is a deliberate decision rather than the incidental one it replaces: the grammar is closed, so an extra component is a claim stow cannot check, and a verifier that ignores the claims it cannot check is verifying a subset of the header and reporting it as the whole.

- **Fixed: presigned authentication parameters were read case-insensitively, so a query could be signed as one parameter and read as another.** `queryValue` was a case-insensitive scan returning the first match, which made `X-Amz-Date` and `x-amz-date` the same parameter. The signed query and the values the verifier consumes are two readings of one string, so a query carrying two spellings could be checked against a value that was not the one signed, and a request could carry two signatures with only one considered. Authentication parameters are read by exact name now, and a name appearing twice — or under another spelling — is refused rather than resolved, because there is no correct choice between two claims and picking one makes authentication depend on iteration order. Ordinary duplicate query parameters are untouched: AWS canonicalizes those by sorting, and that is deliberately not changed.

  The signature comparison is also no longer case-folded. A signature is hex, so accepting one that differs only in case accepts a value nobody computed.

- **Fixed: `CopyObject` was a read followed by a write, so a copy could mix two versions of its source.** Every backend implemented it as `GetObject` then `PutObject`, each taking the store lock separately. A source overwritten in between was copied as the bytes of one version carrying the content type and metadata of another — an object that is neither version of anything. A source deleted in between could report `ErrObjectNotFound` after the read had already produced a buffer, so the answer depended on timing.

  Each backend now captures the source and publishes the destination under one lock, and the contract on `storage.Store.CopyObject` states the guarantee: one version, with its bytes and its metadata always from the same one. Self-copy is a new version of the key rather than a deletion, which is the case a read-then-write gets most damagingly wrong.

  Source preconditions are a new optional capability, `storage.ConditionalCopyStore`, because a caller that read an ETag and then called `CopyObject` has asked for *that version's* bytes, and a store that re-reads the source cannot honour it. Handing the conditions to the store closes the window: the version they were checked against is the version that gets copied. The S3 layer passes `x-amz-copy-source-if-match` / `-if-none-match` straight through, and a `REPLACE` copy checks them against the metadata of the read that produced the bytes rather than against a head taken before it. A store that cannot evaluate conditions still produces a coherent copy, and that weaker guarantee is documented rather than implied. `CopyRequest` is a struct because the two halves must not be confused: a signature taking two adjacent bucket/key string pairs invites swapping them, and a swap still typechecks.


- **Fixed: the upstream S3 client read the machine's ambient AWS configuration, so a profile stow never asked for could stop it reaching upstream storage at all.** `NewS3Client` handed its config to `config.LoadDefaultConfig`, which resolves the entire default AWS chain on top of whatever it is given: `~/.aws/config`, `~/.aws/credentials`, SSO, web-identity token files, and the EC2 instance metadata provider. `UpstreamConfig` is assembled by `envFirst` over a fixed list of `STOW_*`, `S3_*` and `AWS_*` names, and that is the whole of what the documentation says reaches the upstream client — so the machine having an opinion was a divergence between the documented inputs and the actual ones. The observable consequence was that `AWS_PROFILE` naming a profile stow never asked for made client construction fail outright.

  It is worth being exact about which parts of the chain turned out to be inert, because the fix is narrower than the list of mechanisms suggests. Region and endpoint are both set explicitly and they win: a shared config declaring `eu-west-1` still produced a client signing for `us-east-1`, and `s3_use_accelerate_endpoint` in the shared config did not redirect the request away from the configured endpoint. Neither is the bug being fixed, and both are now asserted as invariants — they are the things a future change to the client options could quietly undo, and if the explicit overrides were ever removed they would matter immediately. What was not inert was reading the chain at all.

  The config is now built literally, and `go mod tidy` drops `aws-sdk-go-v2/config` along with its subtree — `feature/ec2/imds`, `service/sso`, `service/ssooidc`, `service/signin` and `service/sts`. The instance metadata provider is no longer in the dependency graph at all, which is a better statement of the fix than the source diff is.

- **Fixed: `Session.close()` abandoned two of its three releases when the first one threw.** Destroying the S3 client, stopping the server, and removing the temporary directory ran in sequence with no isolation, so a rejection from the client left the server process running and the directory on disk. The failure is rare, which is what made it a leak rather than a crash: the caller received an exception, reasonably concluded the session was closed, and left a process and a directory behind. `disposeQuietly`, a few lines below `close()` in the same file, already did this correctly for the failed-start path, so the discipline existed and had simply not been applied where a leak was possible.

  Every release now runs even if an earlier one throws, and the failures are reported together: one failure is rethrown as-is, more than one becomes an `AggregateError`. Reporting only the first is the other half of the defect — a caller who breaks one step should not lose the information that another also broke.

  Four cases in `session-close.test.ts`, each opening a real session and breaking one step deliberately, since the interesting assertion is about the *other* two still having run. Two things about writing them are worth recording. Each test cleans up unconditionally, because the tests deliberately provoke the leak and a leaked server keeps the event loop alive — without a guaranteed teardown the file hangs and the runner reports the still-pending tests as failed assertions rather than as the hang they are. And the leak assertion is written as an explicit `access` rather than `assert.rejects`, because `assert.rejects` reports its own failure as *"Missing expected rejection"*, which reads as though the code under test failed to reject when in fact the rejection happened and the leak was what got observed. Verified red against the original implementation, which left the directory on disk in all three leak cases and reported only the client failure in the fourth.

- **The Python client now has a CI job.** `make test-python` existed and passed locally; nothing in `.github/workflows/ci.yml` ran it, so 43 tests of a shipped SDK surface executed only when a person remembered. The new job mirrors `test-python` exactly: build the binary from this tree, install the client with its `boto3` extra, and run pytest with `STOW_BIN` pointing at what was just built. It runs on **3.10**, the floor `pyproject.toml` declares, because that is the version whose syntax the package has to keep parsing and a newer interpreter would not catch a change that only builds on it. The `boto3` extra is what makes the signing real: the Python client signs with SigV4 and the Go server verifies it, so this is the only job that checks the two against each other through a third implementation.

- **Fixed: a failure to start the server was reported as a bad file descriptor instead of the reason it failed.** `open_session` closed the ready-line descriptor in both its `except` handler and its `finally`. When the spawn itself failed — a missing binary, a file that is not executable, an exhausted descriptor table — the second close raised `OSError(EBADF)` from inside the `finally`, which does not merely add a confusing extra error: it replaces the exception on its way out. So a caller who could not have a session because the binary was absent was told the descriptor was bad, and every diagnosis of "the server would not start" began from the wrong error. The `except` handler no longer closes it; the `finally` already runs on both paths. `test_spawn_failure.py` covers three spawn failures and, separately, counts the closes so that a fix which swallowed the second close instead of removing it would not pass.

- **Fixed: `authority.Ungated` claimed two permissions were described and not granted, after the code had started granting them.** The run-through adapter consults the authority on upstream reads, on upstream writes, and in the retry propagation funnel, but `UpstreamRead` and `UpstreamWrite` were still listed as having no enforcement site. The list is the repository's record of which permissions are *not* enforced, so this was the code asserting a falsehood about itself, in the one file whose purpose is to prevent exactly that.

  The cause was the detector rather than the list. The enforcement test scans source for `<recv>.check(authority.Op)` and matched only a method named `check`; the adapter gates with `Authority.Allows`, which is the package's actual chokepoint. That made the failure worse than a missed detection: the test *requires* an entry in `Ungated` for any operation it cannot see, so it not only failed to notice the enforcement, it required the false claim to stay. A detector whose blind spot corrupts the documentation is not a safe detector.

  The scan now recognises both forms — `check`, which is the runtime's wrapper turning a refusal into an error, and `Allows`, which is the predicate the package exists to make true. It is deliberately a named set rather than "any call mentioning an operation": matching a log statement or a slice would let a real gap pass as enforced. Verified as load-bearing by narrowing the set back to `check` and watching both operations become undeclared.

  Behaviour was never at risk — `internal/runthrough/authority_gate_test.go` has covered these gates behaviourally since they landed, including the funnel case that withholds only `UpstreamWrite`. What was wrong was this file's description of that behaviour. `EnvironmentDestroy` and `EnvironmentPromote` remain ungated, for the reasons already recorded.

- **Fixed: two buckets holding the same escaped key shared one file, so writes clobbered each other, reads returned the other bucket's bytes, and a delete removed an object belonging to a bucket the caller never named.** A key that cannot be a path component — one with a `..` segment, one longer than a path may be, one that would land inside stow's own `.stow` directory — is stored under a digest of the key, and that digest did not include the bucket. The escaped path is now namespaced by a directory per bucket, `.stow/keys/<digest of bucket>/<digest of key>`.

  Natural keys were never affected, because their path already runs through the bucket's own directory, which is why a workspace holding only ordinary keys never showed it. The bucket is hashed rather than used as a directory name so the directory stays within the component limit whatever the bucket is called, and so a bucket name can never collide with stow's own bookkeeping the way a key that resolves to `.stow/keys/…` would.

  The bucket name is stable for this purpose: `ValidateBucketName` admits only `a-z`, `0-9`, `-`, `_` and `.`, so there is no case ambiguity to account for.

  Four key shapes are covered, each non-natural for a different reason so the whole escaped route is exercised rather than one trigger: a leading `..` segment, an interior one, a key that looks like stow's own bookkeeping, and a key longer than a path may be. Each asserts a read from both buckets, that the two objects are two files, and — the sharpest consequence — that deleting in one bucket leaves the other readable. A separate case writes the second bucket first, because two correct reads are still possible if a shared file happens to hold the right bytes, and one asserts natural keys stay per-bucket so a fix for the escaped case is not taken as a reason to change the natural one.

  **Breaking, workspace format:** the manifest version is now **3**, and a version 2 workspace is refused. Its manifest is still valid — the path was always derived from the key and never recorded — but its escaped objects now sit where this build does not look, so opening it would make every escaped key resolve to absent while its file stayed on disk. That is the total-loss reading `ErrManifestCorrupt`'s own comment calls worse than losing bytes, so a clear refusal is the only safe answer. Version 2 was never released, so what this costs is a local development workspace. The refusal test now covers both superseded versions, since they are refused for different reasons and only one of them is a schema this build ever shared; it was verified as a guard by setting the version back to 2 and watching the version 2 case fail.

  Two existing tests hardcoded the old escaped path and failed against the new layout, which is what a layout assertion is for. They now call `EscapedPath` instead of rebuilding the path, so they assert the behaviour rather than a shape that has to be edited on every change.

- **Fixed: `PutObject` deadlocked whenever the file it was writing had no manifest entry or a stale one.** `PutObject` takes the store's write lock, then `putLocked` peeks at the existing object to evaluate its preconditions before it knows what it is overwriting. That peek reaches `resolve`, which re-derives and persists the entry when the recorded one is stale, and `record` takes the write lock again. The lock is not reentrant, so the call blocked forever — and so did every goroutine queued behind it, including `Close`, which meant a test of this path hung rather than failed.

  This is the designed-for workspace case, not an edge case. Stow exists so an agent and stow can share a directory, `stale()` exists specifically to notice a file changing behind stow's back, and adoption exists so a host-written file is readable without a registration pass. Every write over a file the host had touched, and every first write to a file stow had never seen, hit it. The path is `PutObject` → `putLocked` → `peek` → `resolve` → `record`, and the blocked goroutine's own stack names all five.

  The hazard was already known in this package: `putLocked` exists as a separate function for exactly this reason, split out so multipart completion — which holds the lock — could assemble an object without deadlocking on a non-reentrant mutex, and `record`'s comment stated the invariant it was violating ("only called from paths that do not already hold it"). The ordinary write was never converted when it grew the same peek. The fix is the split that was already the established pattern here: `resolve`/`record` take the lock, and `resolveLocked`/`recordLocked`/`peekLocked` are the variants for callers that hold it.

  Three cases in `lock_test.go`, each running the call on its own goroutine with a bounded wait, because a deadlock is not an error return and "the test timed out" says nothing about which lock was taken twice: a write over a file the host rewrote, a write over a file the host only `chtimes`'d (identical bytes, so only the mtime distinguishes it), and a write adopting a file stow had never recorded. All three were verified hanging with a goroutine dump before the fix.

  Writing these tests surfaced a fifth case of a test passing while testing nothing, which is the reason they are recorded rather than just fixed. The default bucket is stored at the root of the workspace, not in a directory named after it, so the first version of the adoption test wrote to a path stow never looks at. `PutObject` then found nothing, created a new object elsewhere, and returned success — a green test that exercised no adoption at all.

- **Fixed: keys containing a space, a percent sign, a plus, or a non-ASCII character were rejected with `403 SignatureDoesNotMatch`.** `buildCanonicalRequest` built the canonical URI from `r.URL.EscapedPath()`, which is *already* percent-encoded, and then `canonicalURIPath` encoded each segment again. A key of `a b` arrives as `/a%20b` and was signed as `/a%2520b`, so the signature could never match. The canonical URI is now built from `r.URL.Path` — the decoded path — and encoded once, which is what the SigV4 specification asks for and what every SDK does.

  The bug was invisible for three separate reasons, which is why it survived: every key in the conformance corpus was made of characters that survive encoding unchanged; the two hand-written signers in `internal/auth` built the canonical URI the same wrong way, so the server and its tests agreed with each other while neither agreed with AWS; and no unit test in `internal/auth` used a key that needs encoding, so the signers' mistake was latent rather than caught. `conformance/encoding_test.go` is the case that closes the gap — it signs with the real AWS SDK, the only independent signer in the repository — and it covers `a b`, `100%`, `a+b`, `café`, a space inside a directory segment, and a key that already looks encoded. Verified red before the fix: all six returned `403 SignatureDoesNotMatch`. Both hand-written signers were corrected to match, with a comment recording why they were wrong, so the next person to add an encoded key to a unit test cannot reintroduce it.

  The `+` case is the sharp one. In a path a plus is a literal plus, not an encoded space, so an implementation that reuses the query-string rules signs `a b` while reading `a+b` — a silent wrong-object read rather than an error. `docs/compat-contract.md` §4.1 now states the canonical-URI rule, since that document owns the wire surface.

- The committed session-density baseline is now compared against a fresh measurement instead of being taken on trust. `docs/benchmarks/session-baseline.json` recorded `rssMiBPerPayloadMiB` — the multiplier a session byte quota must be scaled by to predict peak RSS — and nothing re-measured it, so it could drift without anyone noticing and the number would quietly stop describing the code. `make check-density` re-runs the sweep, compares both derived figures against the committed ones, and restores the file so the check leaves the working tree clean. Both directions fail: a large regression is a defect, and a large improvement means the baseline is stale, which is the same failure as a ratchet that cannot see regressions — the next contributor is handed the wrong number. The tolerance is 25% because the figures are ratios rather than wall-clock, and they are stable: `rssMiBPerPayloadMiB` moved 4.24 → 4.23 between runs on the same machine, so the threshold is roughly a hundred times the observed noise while still catching a real change in what a session costs. The check is deliberately **not** in `make standards`: RSS depends on the machine as much as on the program, and a required check that fails on a loaded shared runner is worse than none — this repository has already spent a release cycle on a required check that could never pass. It is the same reasoning that keeps `make benchmark` out, applied to the gap that made it need a comparison at all. Verified as a guard by tightening the tolerance to 0.1%, which fails on a 0.7% drift.

- The run-through adapter now consults the environment's authority before it reaches an upstream provider, and there is one mechanism answering "may this reach upstream" rather than two. Writes were gated by `Policy × AllowLiveWrites` and reads were not gated at all; `UpstreamRead` and `UpstreamWrite` were defined, exported, and checked nowhere in the package, so a caller narrowing an `Authority` appeared to withhold something the adapter never consulted. The grant is resolved once, at construction, with `AllowLiveWrites` folded into it there; every upstream decision — the read-through path, the propagation decision, and the outbox retry funnel — consults only that one value. `RetryPending` is the substantive part: it bypassed even the write decision, and it runs from the per-second retry worker and the admin retry route, both outside the runtime instance, so a pending entry could be propagated by a path that had checked nothing. A refused entry is now left pending rather than failed, so a write withheld for want of a grant is not discarded if the grant is later given. Refusing consent to change someone else's data still leaves reads alone, because a read-through cache over a locally authoritative write depends on it. The authority lives on `Config` rather than as a sixth argument to `NewWithOutbox`, which would have breached the parameter ceiling for no behavioural gain; what matters is that it is read in exactly one place, and ADR 0010 decision 2 records why that shape was chosen over a live closure and over inverting the construction. Six cases hold the gate, each asserting on the provider rather than on the absence of an error.

- The four remaining untested gates now have tests, and two of them had a defect in how they were built rather than only a missing test. `check-coverage` decides whether a change may reduce what is tested and had no test at all: the decision lived inline between the measurement and the exit code, so the only evidence it had ever given was a number in a CI log. It is now a pure function with eleven cases, including the two that matter most — losing covered statements fails even when the percentage holds, and a *lowered stored baseline* fails even when the tree meets it, which is the one way a loss can be made to stick. `check-version` compares four versions found by regex over source files, so the failure it has to survive is a pattern that quietly stops matching; the comparison is now pure with eight cases, and writing them exposed a flaw in the extraction: once the Go version is unreadable, comparing everything *to* it is not information but the same unreadable value failing four times, so the comparisons are now suppressed and only the independent Python pair is still checked. `pack-platform-package` maps a release archive name to an npm platform package, which is the only place the `amd64`/`x64` spelling difference is caught before a release; seven cases cover every released target. `publish-if-absent` exists so a release is re-runnable, and its plan is now separated from the publishing and tested against real tarballs with the registry lookup injected — first run publishes everything, second run publishes nothing, and a partial release retries exactly the package that is missing. Both release scripts ran their entry point on import, which meant they could not be imported and so could not be tested at all; the entry points are now guarded and the direct invocations still exit 64 on missing arguments. `scripts/*.test.mjs` is at 59 cases, from 16.

- **Breaking, workspace format.** The workspace manifest and its object index are separate documents at layout version 2, and a version 1 workspace is now refused. They were one file, so adopting a single host-written object rewrote the whole workspace's metadata: 20 `HEAD`s against 20 host-written files produced 20 full rewrites, each serialising a document that grew as it went, with every `HEAD` taking the write lock. Identity changes once per workspace; the index changes per object. Adopting 20 objects now leaves `manifest.json` untouched and writes only `index.json` — measured, and asserted by a test that fails if the identity document's modification time moves. A version 1 workspace will not open, and the refusal says its files are still on disk and that removing the directory is the whole fix, because refusing a directory full of files would otherwise read as data loss. It is refused rather than migrated deliberately: carrying its recorded checksums, ETags and metadata into `index.json` needs a rewrite that can be interrupted with the index as the only copy, and treating a missing index as empty would discard them silently. Adoption itself is unchanged — a workspace whose files need registering before they can be read is not a working directory — and `HEAD` still reads the file to derive an ETag, because a correct ETag cannot be produced without the bytes. What changed is that recording the result no longer rewrites the workspace's identity.

- Object and manifest writes now share one atomic-write implementation, and it reports the errors it used to discard. Two functions of the same name and intent offered different guarantees. The filesystem backend synced the parent directory after rename and threw away both the `os.Open` and the `Sync` error, so a directory sync that failed returned success. The workspace manifest renamed with no directory sync at all, and a rename is not durable until the directory entry is synced — so every workspace object and manifest write was exposed to a power cut that the filesystem backend survived, and nothing said so. `internal/atomicfile.Write` performs temp → write → chmod → fsync → close → rename → fsync parent and returns every error, naming the file that failed so a caller holding many paths can tell which write broke. Both backends delegate to it, which covers all five workspace call sites — objects, manifest, registry, and both multipart state writes — through a single change. The mode is now applied before the sync rather than after the close, so there is no window in which the file is on disk with the wrong permissions; the workspace copy had that window and the filesystem one did not. The temporary file is removed on every failure path through a single deferred cleanup, so a new error path cannot forget it.

- The gates now share one list of what they scan, and it covers the code that was not being checked. `tools/quality` and `check-file-size` each carried their own list of roots, and they disagreed: `tools/` and `scripts/` were in neither, so `tools/quality` — the code that checks every other file's complexity, parameter count, length and use of `any` — was itself outside the ratchet, as was every script in `scripts/`. Both read `config/scan-roots.json` now, and a missing or malformed file is an error rather than a fallback, because a fallback would restore the two-copies problem quietly. Verified by planting oversized files in both previously-unwatched directories: `new oversized file: scripts/__probe.mjs:521` and `new oversized file: tools/quality/__probe.go:523`. Bringing `tools/` under the ratchet cost one violation — `scanFile` at complexity 17 against a ceiling of 15 — which was four closures whose logic had nothing to do with walking a file, and a closure's branches count towards its enclosing function. They are a `checker` type now, with `add`, `checkFunction`, `checkLiterals` and `checkEscapes` as methods, and the ratchet is unchanged at 16 entries. Four cases in `scripts/scan-roots.test.mjs` pin the shared list: that `tools/` is in both consumers, that every named root exists on disk, and that the Go list covers every Go source root. A gate carrying a path that resolves to nothing checks less than it appears to, and looks like coverage while doing it.

- **Breaking, test.** The 100-session session-lifecycle stress tests had never been given their timeout. Both were written `it(name, async () => {...}, { timeout: 300_000 })` — the function second and the options third, which is the reverse of `test(name, options, fn)` — so `node:test` received the options where it expected the function and the 300-second limit was silently discarded. They were the two slowest tests in the suite, and the timeout exists for exactly the case where they get slow. Argument order is now correct. This was found by type checking the test suite for the first time; it is invisible to every current gate, because the tests compiled to nothing.
- The TypeScript test suite is now type checked. `tsconfig.json` included `src/**/*.ts` and nothing else, and `npm test` runs the suite through `tsx --test`, which strips types without checking them, so thirteen test files were compiled by nothing while `strict` and `noUncheckedIndexedAccess` protected the shipped code and not the code that tests it. Verified before changing anything: `const wrong: number = "not a number"` in a test file passed `tsc --noEmit` with no diagnostic. `tsconfig.test.json` now covers `src` and `test` and runs in `check:standards`, and it is green. Turning it on found three more problems: the timeout defect above, a `GetObject` body dereferenced without a presence check (so a bodiless response would have failed as "cannot read transformToString of undefined", naming the wrong thing), and a `.mjs` build script imported with no declaration — fixed with a four-line `.d.mts` rather than by enabling `allowJs` across the package.

- Supplying a credential provider together with static credentials is now expressible from the public type, and a configuration with no usable credentials is refused where it is built rather than by the AWS SDK later. `AwsSdkV3ConfigOptions` forbade the combination with `provider?: never` and `accessKeyId?: never`, while `buildAwsSdkV3Config` has always resolved the conflict in favour of the provider and a test asserts that precedence — so behaviour the implementation performed and its tests depended on was unreachable from the public API, and the test could only have been written by casting around the type it was exercising. Verified before changing anything: `Stow.awsSdkV3Config({ endpoint })` with no credentials returned a config whose `credentials` was `{}`, and the failure surfaced later as an SDK message about credential resolution, several frames from the cause. It now throws `StowCredentialsError` at construction, naming what to supply. The realistic way to reach this is environment variables that are unset, which arrive as `""` rather than `undefined` — the type is satisfied and the credentials are still useless — so the test asserts that case and needs no cast. The escape ratchet caught a double cast in the first version of that test and refused it, which is the gate doing its job on the author.

- The lint ratchet counted suppressions by matching `eslint-disable` text with a regular expression, and now counts them from ESLint's own report. The regex could not see a disable block whose rule name is on a line below the directive — its pattern was `[^\n]*?`, so it stopped at the newline — and a suppression placed that way was invisible to the gate entirely. Verified against a directive written across two lines: the old expression matched it zero times, and the gate now reports `new debt: no-console: 2 > 0` for the two calls it was hiding. The regex also matched any line that merely mentioned a ratcheted rule name beside the word `eslint-disable`, including inside a string or an unrelated comment, and it charged one count per comment however many violations the comment hid, so a single directive could suppress an unlimited number of findings for the price of one. `report.suppressedMessages` is ESLint's own accounting — one entry per suppressed message, carrying the rule that would have fired — so a disable hiding five calls now costs five, and a directive the linter never applied costs nothing. The counts in the checked-in baseline are unchanged, because there are no suppressions in the tree; what changed is that adding one is now detected on every syntactic form rather than the subset the regex could reach.

- Every authority operation is now either enforced somewhere or declared ungated with a reason, and a test fails when that stops being true. Four of the twelve defined operations had no enforcement site at all — `environment.destroy`, `environment.promote`, `upstream.read`, `upstream.write` — and nobody knew, because the set is closed and the constants are exported, so a caller narrowing an `Authority` appears to withhold something the code never consults. The gate metrics cannot see this: there is no line of code to be too long or too complex. `authority.Ungated` now names each one with the work that closes it, and the check is a source scan rather than a hand-maintained list, because a hand-written "these are enforced" list would be a fourth copy of the same fact. The scan reconciles Go constant names against operation values — a call site reads `check(authority.BucketCreate)` while `Defined()` reports `bucket.create`, and skipping that step makes every operation look unenforced, which is how the first version of this test passed four assertions while finding nothing. Verified as a guard by adding an operation with a bit and no check site:

      operations with no enforcement site and no entry in authority.Ungated: "probe.unwired"

  Two further cases keep the list honest in both directions: an operation that has become enforced must be removed from `Ungated`, or the list stops meaning anything; and the ungated set is asserted to be exactly the four known gaps, so it cannot drift upward unnoticed and a change to it has to be somebody's decision. M1.3 enforces three of the four and M4.3 removes `environment.promote`, which is deleted rather than wired until it has an implementation — a permission for an operation with no implementation is a claim about behaviour that does not exist.

- The ratchet policy is now written once and tested, instead of four times and not at all. `check-lint-ratchet`, `check-dry`, `check-file-size` and `check-type-escapes` each enforced the same three-part decision — has new debt appeared, has an improvement gone unrecorded, has the baseline itself grown — and each had written it out by hand: two compared per-key counts and two compared identity sets, and all four grew the baseline-growth check separately. This is the failure the architecture document names in its own repository: a decision with one correct answer written down more than once by hand, where every copy is small, every copy is individually plausible, and no gate can see the others exist. The policy had no test, which is worse than having four copies of an untested policy rather than one — a gate that has quietly stopped rejecting new debt is worse than no gate, because the debt is still described as baselined. `scripts/ratchet.mjs` now holds the decision as pure functions and sixteen cases cover it, including the two directions that matter: a reduction is a failure until the baseline is lowered, and a baseline raised to match new debt satisfies the per-key comparison while the comparison against history catches it. A renamed violation is caught on identity rather than on count, which is asserted directly, because a count-based check sees one addition, one removal and no change. `compareIdentities` now deduplicates, so a scan that reports the same identity twice cannot read as two violations — the type-escape scan passed a plain array and could have done exactly that. All four gates produce the same results as before through the shared module, and the file-size gate was re-verified as a guard by planting a 523-line file and watching it fail.

- `tools/quality` had no test, and the ratchet it implements is the gate every other gate is trusted because of. The comparison lived inside `main`, so there was nothing to call and nothing to assert. It fired three times in a single session — cyclomatic complexity 4 > 3, max-params 10 > 8, and a new oversized file — and each time the code caught it; nothing would have noticed if the code had stopped catching it. The comparison is now two pure functions, `ratchetProblems` and `countIncreases`, and thirteen cases cover the four behaviours: an unchanged tree passes, a new identity fails, a stale identity fails, and a per-rule count increase fails. Two of them are about the directions that matter rather than the happy path. A *renamed* violation is caught by identity rather than by count, which is asserted directly, because identity matching alone would see one new entry and one stale entry and an unchanged total — only the per-rule count notices the rule did not get better. And a reduction must pass, or fixing debt would fail the gate. `scan` is now `scanRoots` behind a fixed root list, so the metrics are provoked on a temporary fixture instead of on the repository; a fixture inside the tree would be scanned by the gate itself and would need a baseline entry of its own, which is a debt recorded in order to test the thing that records debt. The last case asserts the checked-in baseline still describes the tree, since a stale entry there is the signal that lowers the floor. Report ordering is now sorted, because iterating a map to build an error message makes the same tree fail differently on different runs.

- A release can no longer publish while recording that it was never verified against a real provider. The live-conformance gate is wired into the release's `needs` and reports honestly — it emits `SKIPPED - no live provider was configured, so this release is NOT verified against one` and raises a workflow warning — but it was configured with `require_configured: false`, so a repository without `STOW_LIVE_*` secrets skipped the gate and the release went out anyway. The honesty was in the notes; the consequence was in the gate. The gate is now enforced by default, so a missing live configuration fails it rather than skipping it. This was previously turned off deliberately, on the reasoning that enforcing it made every release impossible — which holds only while `STOW_LIVE_*` is unset, so the cause is unconfigured secrets rather than the flag, and a maintainer who configures them is unaffected. For a maintainer who genuinely has no live credentials, setting the repository variable `STOW_ALLOW_UNVERIFIED_RELEASE=true` downgrades the gate to a skip; the release notes still record the skip and the workflow still warns, so a deliberate downgrade is visible in the published notes instead of being the default. The `STOW_CONFORMANCE_UPSTREAM=1` suite is also the only thing that can confirm the two known S3 divergences in the compat contract against a real provider, so enforcing this gate is what turns those from documented suspicions into verified facts.

- A read-only workspace could not be opened. `WorkspaceOptions.Authority` documents the configuration directly — "pass `&stow.ReadOnly()` to hand out a workspace an agent can read but not change" — and it failed in the constructor: `stow: create workspace bucket: operation "bucket.create" is not permitted`. `OpenWorkspace` builds the runtime with the caller's authority and then created the workspace's own bucket *through that runtime*, so the grant was evaluated against the act of issuing it, and the narrowest documented workspace was the one workspace that could not exist. The bucket is a construction step, in the same category as `initialize()`, so it is now bootstrapped through the store and never consults the grant. It was not fixed by widening `ReadOnly` to include `bucket.create`: that would satisfy the same symptom while handing a read-only workspace the ability to create buckets, so the test asserts the refusal half too — the workspace opens, serves a host-written file, and refuses `PutObject`, `DeleteObject`, and `CreateBucket`. It survived as long as it did because the workaround is discoverable: a read-only environment cannot create a bucket, so a caller can seed one through the store first, and one test in `pkg/stow` carries that workaround as a comment rather than as a bug report.

- `CompleteMultipartUpload` discarded the error from listing an upload's parts, which silently disabled the check that listing existed to serve. The handler builds a part-number-to-size map and uses it to enforce S3's 5 MiB minimum on non-final parts; the `ListParts` error was dropped on the floor, so a failure produced an empty map, every size lookup missed, and the minimum was not enforced at all. A client could complete an upload made of 1-byte parts — the one thing the check prevents — and the failure that had disabled the check was itself invisible, because the request carried on to completion and reported success. Any I/O error reading the upload directory reached this path, so it was reachable rather than theoretical. A store that cannot list the parts cannot be asked whether they are big enough, so the error is now reported through the normal mapping: a missing upload answers `404 NoSuchUpload` at the point the client asks rather than after a wasted round trip through completion, and an unmapped failure answers `500`, which is the honest answer when the request was well formed and the store broke. Two cases were added at the same time to hold the check itself — that two undersized parts are still refused with `EntityTooSmall`, and that a lone final part is exempt, since S3's minimum applies to the parts a client intends to keep appending to and refusing the last one would make every small upload impossible.

- A `Range` header whose end ran past the last byte was refused instead of clamped. `GET` with `bytes=0-999` on a 50-byte object answered `416 Requested Range Not Satisfiable` where S3 answers `206 Partial Content` with all 50 bytes. RFC 9110 requires a recipient to treat an unsatisfiable *end* as the last byte, and this was reachable without doing anything unusual: a resumable download that knows a length, or a media server answering a seek, both name an offset they have inferred rather than measured. The suffix form (`bytes=-N`) already clamped, and a start at or past the size was already a correct `416` — the parse treated the two directions of an over-long range identically, so the one case that should clamp and the one that should not were decided by the same expression. They are now separate, and the two directions are pinned apart: clamping the start as well would answer `206` with an empty body where S3 answers `416`, which is a different bug in the opposite direction. The compat contract said "Invalid or unsatisfiable range: 416" without saying which was which, which is ambiguous enough to have produced this, and its conformance cases covered a start past the end but never an end past the last byte. Both are fixed: the contract now states the clamp and the `416` conditions explicitly, and two conformance cases were added for the clamped end.

- `CopyObject` could not copy any key that needed encoding. The `x-amz-copy-source` header carries a percent-encoded key, and the compat contract says so, but `parseCopySource` split the header on the first slash and used both halves verbatim. Every SDK percent-encodes the key, so a key containing a space, a plus, a percent sign, or a slash could not be copied at all: the server looked for a key literally spelled with the escapes still in it and answered `NoSuchKey` for an object that existed. The request path was already handled correctly — `parseRoute` splits the raw path and then decodes each half — so the same decision was implemented twice and one copy was missing its second half. The header is now split before it is decoded, never the other way round: decoding first would turn an encoded `%2F` inside a key into a separator and land the split inside the key, so a key with a real slash would work and a key with an encoded one would not. It is `PathUnescape` and not `QueryUnescape`, because in a path segment a plus is a literal plus rather than an encoded space, and the query form would rewrite a key spelled `a+b` into `a b` and copy the wrong object — which is why the test cases include one. No test issued a `CopyObject` at all, so the operation had no wire coverage; the cases added here run against the memory backend with a table of encoded keys, and a missing source still answers `404` so the decode cannot become "accept anything".

- **Breaking, data loss in the response.** A multi-object delete reported the inverse of what it did, on one of the three backends. `DeleteObjects` returns the keys it confirmed deleted, and the S3 handler copies that slice straight into the `<Deleted>` elements of the response — but the workspace backend returned the keys that *survived*. A client deleting three objects was told it had deleted the one that was never there, and told nothing about the two that were actually gone. The deletions themselves were correct; the report was the complement. `DeleteObjects` had no doc comment on the `Store` interface, so the meaning of its return value was unspecified and three implementations chose: two returned one list, the third returned the other, and nothing said which. The same omission lost the partial-progress case — a failure partway through returned `nil` instead of the keys already removed, so a caller retrying the remainder could not skip what had succeeded, turning a recoverable partial failure into a second round of deletes against keys that were gone. The interface now documents both halves, and a contract case plus a wire case across all three stores hold them.

  A key that was not there is **confirmed**, not skipped: S3's `DeleteObjects` reference states that a missing key is "returned as deleted", so it belongs in `<Deleted>`. All three backends now agree on that, and quota is released only for keys that actually existed — `internal/runtime` decremented `usage.Objects` for every returned key, which with absent keys included would have let a caller inflate its own quota by deleting keys that never existed. The workspace backend's own test had recorded the complement as expected behaviour, deleting a key, confirming two lines later that it was gone, and asserting that the *other* key was the one returned, so the defect was pinned rather than merely uncaught. Four other tests across three packages encoded the same wrong expectation, including one that deleted a key named `missing` and asserted it was not reported.

- A multipart completion with exactly one part returned the wrong ETag on two of the three backends, and no backend rejected a completion with no parts at all. S3 treats a one-part completion as a single-part object and returns that part's own ETag verbatim; the `-{partCount}` suffix belongs to genuinely multipart objects, where the digest covers the concatenated part digests. The memory and filesystem backends returned `md5(md5(body))-1` where S3 returns `md5(body)` — a double hash, with a suffix. The workspace backend had it right, in a `len(parts) > 1` conditional the other two did not share, so the rule was written three times and correct once. It is now one function, `storage.CompletionETag`, called by all three, and the correctness of the previously-correct backend is pinned by a contract case so it cannot silently regress back. The returned value changes for single-part completions, so a client that stored the old ETag will get `412` on a conditional write until it re-reads; that client was already holding a value S3 would not have issued. Separately, the emptiness check existed in two backends and was missing from the third, so the same empty completion produced a `500` on two stores and a zero-byte object published under the caller's key on the third. That check now lives in `ValidateMultipartPartNumbers` and returns `ErrInvalidPart` rather than `ErrInvalidUpload`, which the S3 surface does not map and which therefore fell through to a 500 — misreporting a malformed request as a server fault and inviting a retry that could never succeed. Both rules were absent from the contract suite, so all three backends passed it.

- **Breaking, install.** Every documented install path was unresolvable. `site/agent.md` and `site/llms.txt` — the two files an agent is most likely to be handed first — opened with `npm install @chs/stow-s3`, `pip install stow-s3` and a `go get`, and all three failed: nothing was published to npm or PyPI, and the Go module path was `.../stow-s3` while the repository was still `.../stow`, so no published version of it could resolve. An agent following the instructions stopped at the first one, and the failure presented as a registry or network problem rather than a documentation one. The repository is now `chester-hill-solutions/stow-s3`, matching the module path, the npm scope, the PyPI name and the binary — every user-facing document already said so, including the repository URL. The Go module is published and installs. Since that note was written, the `v0.2.0` workflow partially published the main npm package to GitHub Packages but failed before publishing platform packages; PyPI remains unpublished, so the npm and Python install surfaces are still not usable. The documentation records that partial state; the TypeScript and Python clients are usable from a source checkout, and all three paths were run end to end before being documented. The `v0.1.0` tag predates the rename and cannot be fetched under the new module path; `@latest` and `v0.2.0` are unaffected. `scripts/check-install-surface.mjs` makes publication status a single declared fact and fails when the documentation and that declaration disagree, which is the check this was missing; the release workflow additionally resolves each published target against its registry. See issue #3.

- **Breaking, macOS.** The parent-death watch was never armed on macOS, and the server logged itself as protected while it was not. `Watch` had two independent defects at once. It registered an `EVFILT_PROC`/`NOTE_EXIT` filter and then closed the kqueue descriptor as it returned, with nothing ever reading the event; kqueue filters are scoped to the open descriptor, so closing it discarded the registration. And it read `kevent()`'s return value as a count of registered changes when the kernel reports how many events it placed in the eventlist, which is always `0` for a registration-only call, so every pid including the real parent was rejected with `ErrNotParent`. Either defect alone is fatal, and fixing only the descriptor would have left the watch broken while looking correct. The descriptor is now held for the process lifetime with a goroutine blocked on it, raising `SIGTERM` when the parent exits — the same disposition `PR_SET_PDEATHSIG` produces on Linux, so both platforms terminate identically whatever the server's own signal handling is. The arm/death race is closed by re-checking the parent after registration, as Linux does. A kqueue error after a successful arm is now fatal rather than silent, because continuing would leave a server that believes it is watched and is not. macOS is a first-class release target, so this leaked a process and a data directory on every killed session. A `macos-latest` CI job was added, because every job ran on ubuntu and the kill test therefore never executed on the platform whose implementation it exists to protect; `release.yml` only cross-compiles darwin, which proves the binary builds and nothing about its lifecycle. The new job failed on its first run and is what found the `kevent()` defect. See issue #4.

- The filesystem backend rejected object keys between 128 and 1024 bytes, even though `ValidateKey` accepts up to 1024. The key was hex-encoded into a single path component and hex doubles the length, so anything over 127 bytes failed with `ENAMETOOLONG` and surfaced to the caller as a `500` for input it was entitled to send. It also broke interchangeability between the two drivers: the embedded driver is memory-only, so the same call succeeded on one and failed on the other. Long keys are now split across shard directories holding chunks of the same reversible encoding. Shard directories carry a prefix that cannot occur in hex, which matters more than it looks: without it a record file and a shard directory share one name space, so a key whose encoded length fell exactly on a chunk boundary wrote its record *file* to a path that a longer key sharing the same hex prefix had to descend through, and the longer write failed with `ENOTDIR`. Because hex preserves order, any two keys with a common byte prefix collide, so this was the common case rather than an exotic one. A path component's form now decides whether it is descended into, with no `stat` required. Keys that fit stay flat, so existing data directories are unaffected: long keys never wrote successfully, so no stored object depends on the layout. Deletes prune the shard directories they empty, which would otherwise accumulate for the life of the data directory, and the list walk descends only into shards it recognises. No test covered a long key anywhere, which is why this reached a release. See issue #5.

- `check-generated`, and the CI step that diffs the committed WebAssembly artifact, could never pass. Four of the seven required checks on `main` were permanently red, and had been since before `0.2`. Two independent causes, neither of them a source change. The Go version was never pinned: `go.mod` said `go 1.24` and all ten `setup-go` steps used `go-version-file: go.mod`, which resolves to the newest `1.24.x` rather than a fixed patch, so a locally built artifact never matched a CI rebuild. Adding a `toolchain` directive on its own would not have fixed it either, because Go uses a newer installed toolchain instead of downgrading to the one named. `.go-version` now pins the exact patch for every step in `ci`, `release`, and `live`, and the `toolchain` directive in `go.mod` makes a local build fetch that same patch. Separately, `copy-wasm-assets.mjs` used `copyFile`, which carries the source mode across, and the two places `wasm_exec.js` comes from disagree about it: the tarball toolchain ships it `0755`, the module-cache toolchain `0444`. Git records only the executable bit, so on a fresh checkout the copy gained the bit and the diff failed on a mode change with identical contents — which is why the gate passed in a working tree and failed on the runner. The copy now sets the mode explicitly, and both committed assets are `0644` rather than the previous mix of `0644` and `0755`. See issue #6.

- The TypeScript client now honors `timeoutMs` and `signal` on `openStow` and `withStow`. Both were declared on `EphemeralStowOptions` and never forwarded to the spawner, so a caller's timeout was silently replaced by a hardcoded ten seconds and an abort signal did nothing. An already-aborted signal now fails before a process is spawned, and an abort during startup stops the child rather than leaving it running.
- The client honors the region the server reports. The readiness protocol carried a `region` field, the client parsed it, and then discarded it in favour of a hardcoded `us-east-1`, which signs against the wrong region for any non-default server. The server gained `--region` so the field can actually vary, which is what made the behavior testable; the default is unchanged.
- The readiness descriptor is no longer parsed mid-record. A chunk boundary can fall anywhere, and the trailing unterminated fragment was being handed to the JSON parser; a syntax error there was thrown from a stream callback, so the rejection never reached the promise and startup hung until the timeout, already cleared. Only a newline-terminated record is parsed now, a parse failure rejects, an oversized record without a newline is reported as a protocol violation rather than silently truncated, and the descriptor's `end` and `error` events are handled. The `end` case defers by one turn so a child exit is still reported as a child exit rather than as a pipe failure.
- `StowProtocolError` gains a `cancelled` code. Cancellation was reported as `internal`, which tells a caller nothing about whether retrying could ever help.
- **Breaking, security.** Admin and metrics routes now require a credential. `--allow-public-admin` was a bare boolean and the only gate, so enabling it exposed the `outbox/retry` and `outbox/discard` actions to any client that could reach the port, with no authentication. The flag is now deprecated and ignored. Remote admin routes require `STOW_ADMIN_TOKEN` or `--admin-token`, sent as `X-Stow-Admin`; the two outbox routes require it on loopback as well, since loopback is not a privilege boundary. Read-only routes (`health`, `status`, `inspect`, `metrics`) still work on loopback without a token, so `stow doctor` needs nothing. Rejections are `404` rather than `403` so the route's existence is not advertised, and the token comparison is constant time.
- **Breaking, security.** CORS no longer reflects the request's `Origin`. It previously echoed whatever arrived, or sent `*` when the header was absent, so any website a developer visited could read responses from their local stow — including bucket contents — using the credentials the SDK had already placed in the page. Loopback origins are permitted by default, which is the case a local dev server has; anything else must be named with a repeatable `--cors-origin`, and `*` restores the old behavior only when asked for explicitly. Every response now carries `Vary: Origin`, without which a cache can serve one origin's allow header to another, and a preflight from a disallowed origin is refused with `403`. This wires `Config.CORSOrigins`, which was declared and never read.
- **Breaking, safety.** `STOW_POLICY=mirrorWrites` no longer enables live upstream writes on its own. Previously the policy set `AllowLiveWrites` whenever `STOW_ALLOW_LIVE_WRITES` was *unset*, so the absence of a variable was the enabling condition, and a staging `.env` containing the policy plus shared credentials was enough to propagate mutations to a real bucket under the default auto-detected mode. `STOW_ALLOW_LIVE_WRITES=true` or `--allow-live-writes` is now required and is sufficient under either policy; an explicit `false` is a refusal the policy cannot override. Reads still use run-through, and writes still succeed locally. See `docs/adr/0005-live-write-requires-explicit-consent.md`.
- Report the effective write policy from one place. The banner, the server status payload, and startup validation each derived it independently, which is how the banner could claim `mirrorWrites` while the adapter refused the write. A configured-but-inert policy now reports `mirrorWrites-disabled` instead of reading as active.
- A run-through server on the memory backend with `mirrorWrites` configured and no live-write consent now starts instead of being refused. It performs no propagation, so requiring the filesystem backend for it was rejecting a configuration that works.
- **Breaking, safety.** `Stow.start({ cleanSlate: true })` was an unguarded recursive delete of whatever path the caller passed, including the home directory, and was reachable from the published `dist/`. A reset now requires a `.stow-owner` marker that the server writes when it initializes a data directory, and refuses the filesystem root, the home directory, the working directory, and any ancestor of them. `resetOwnedData` is the new name; `cleanSlate` is a deprecated alias with identical checks. A pre-existing data directory without the marker is refused rather than deleted, so upgrading requires one manual removal. See `docs/adr/0006-owned-data-directory-reset.md`.
- Local mode is now proven to make zero upstream requests rather than assumed to. Store construction is one function that never builds an upstream client in local mode, and a test sets the full hazardous environment, exercises the object operations against a recording upstream, and requires zero hits.
- Close the 0.2 remediation gate with race-safe server lifecycle, atomic filesystem object records, backend parity checks, write-ahead durable outbox recovery, ordered per-key propagation, admin metrics/retry controls, and expanded conformance coverage.
- Add a memory-only direct embedded Go runtime with explicit paginated results, bounded/TTL separate run-through caches, and a versioned `js/wasm` host bridge without changing the process/endpoint TypeScript contracts.
- Coordinate file-backed outbox workers across processes with expiring per-entry claims and a filesystem lock.
- Reconcile an attempted outbox entry against upstream before re-propagating it: a retried put whose upstream ETag already matches the immutable local version, or a retried delete whose object is already absent, is acknowledged instead of replayed. The remaining duplicate-delivery window is an upstream that cannot be read during recovery, or an object another writer has since replaced.
- Reject durable outbox files written by a newer schema revision instead of silently dropping claim and reconciliation fields; unversioned files migrate, and attempted legacy entries are marked for reconciliation.
