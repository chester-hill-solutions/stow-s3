# Stow v0.3.3

This release improves the existing storage, COPY, multipart and recovery paths.
It also reduces allocation costs in measured filesystem and run-through workloads.

## Distribution

Native GitHub downloads target Linux and macOS on x86_64 and ARM64. Verify each
archive against this release's `SHA256SUMS.txt`. npm and PyPI publication remain
deferred; use a source checkout for the TypeScript and Python clients.

## Reconciled cleanup and snapshot fixes

This release combines the core quality work from PR #78 with PR #77's existing
cleanup, multipart identity, snapshot and preparation/checkpoint admission fixes.
The v0.3.2 tag was created before #77 was included; its publication workflow was
cancelled and no GitHub release was published. The public tag remains fixed.

- Queue concurrent worker stream cleanup within its bounded control lane, retain
  dispatched ownership until acknowledgement, and permit retries after failed
  persistent read releases.
- Detect same-size, timestamp-preserving host edits to multipart objects using a
  separate byte fingerprint. Live reads and read-only snapshots derive matching
  content type, metadata and identity regardless of prior HEAD requests.
- Admit preparation input sizes/counts and immutable Git trees before expensive
  copying, hashing or checkout; account for fetched Git metadata and checkpoint
  limits before proceeding.
- Retain #78's newer namespace admission, uncertain-outcome fences and multipart
  buffer publication. PR #77's older namespace fix is already covered there.

## Correctness changes

- Keep COPY source conditions and captured source versions consistent through
  run-through fallbacks, without the costly conditional emulation path.
- Refuse ambiguous object absence before mutation and retain committed identities,
  multipart outcomes and quota accounting when a later operation reports an error.
- Reject premature EOF and excess bytes in buffered and streamed reads; close
  source readers when opening or propagation fails.
- Preserve unknown recovery state and require reliable absence before recovery
  removes or replaces saved state.
- Enforce combined quotas on reopen and apply namespace capacity admission to
  durable saves, multipart and bucket lifecycle operations. Retain reservations
  after uncertain publication and directory-fence errors.
- Reject corrupt, empty or identity-inconsistent outbox journals, migration
  collisions, exhausted fencing tokens and empty ownership credentials.

- Verify handoff archives against an expected SHA-256 digest, count archive payload
  files consistently, and preserve caller-supplied session data directories.
- Permit a bounded limit when resuming a workspace whose persisted limit is
  unlimited.

## Measured efficiency changes

- Stream metadata-replacement COPY and large run-through reads; remove redundant
  buffered-read and validated upload-body copies.
- Reuse verified journal bytes, narrow snapshot cloning and unchanged durable
  state; write compact framed protobuf outbox snapshots.
- Reuse verified capacity usage, stream resource hashing and avoid concatenating
  multipart payload buffers during publication.

For the 64 MiB, one-part namespace-bound multipart fixture, allocations fell from
201,614,584 to 67,382,936 bytes and whole-child peak RSS from 141.46 to 77.28 MiB.
Median time changed from 1268.808 to 1241.225 ms. These Railway measurements cover
that fixture; they do not establish a general throughput improvement or constant
memory use. Small adverse timing results are retained in the
[completion report](https://github.com/chester-hill-solutions/stow-s3/blob/v0.3.3/docs/reviews/2026-10-18-completion-buffers.md).

These measurements qualify the named individual filesystem change. The
combined release has not been rebenchmarked after branch reconciliation.

## Compatibility

Legacy workspace multipart entries without a content fingerprint are re-derived
once and may receive a different ETag/version or lose unverifiable saved metadata.
Snapshots of actual host edits discard stale metadata and derive content type,
matching live reads; snapshot reads remain read-only.

Outbox writes use schema 4 (`STOWOUT4`) framed protobuf. Legacy JSON schemas 0–3
remain readable and migrate on the next successful write. Older releases cannot
read the new journal format. Back up persistent data before upgrading if a
rollback may be necessary, and run the same revision in every process sharing
an outbox journal. The existing filesystem object-record v2 downgrade restriction
also continues to apply. `CheckpointArchiveOptions` gains an `ExpectedSHA256` field;
`ErrHandoffDigestMismatch` reports mismatches. Positional struct literals may need
updating. No dependency is added. See the
[outbox migration report](https://github.com/chester-hill-solutions/stow-s3/blob/v0.3.3/docs/reviews/2026-10-17-outbox-protobuf.md).

## Known correctness issues

The bounded [closure review](https://github.com/chester-hill-solutions/stow-s3/blob/v0.3.3/docs/reviews/2026-10-18-correctness-closure.md) reproduces
four issues that remain in this release:

- **High:** workspace reads can mistake permission/I/O errors for absence;
  a create-only write can overwrite an existing unreadable destination.
- **Medium:** SigV4 authentication covers only the first value of a repeated
  header, rejecting valid multi-value signatures and accepting appended values.
- **Medium:** case-insensitive opaque ETag comparisons produce incorrect PUT
  and COPY precondition outcomes.
- **Low:** query-name ordering before URI encoding rejects valid SigV4 signatures
  for some encoded query names.

The review records exact scope, healthy controls and Railway normal/race evidence.
It is not a certification of physical-crash recovery, every platform or live
provider compatibility. This release makes no executed-live-provider claim.
