01

An agent's working state is the one thing you can't get back.

The run produced something. A report, a patch, a dataset, a half-finished refactor. Then the job ended, and it went into the runner's scratch directory, which is not a place you can come back to.

The usual alternatives are worse than losing it. Point the agent at a cloud bucket and you have handed an agent's intermediate output to someone else's account, with their retention policy and their blast radius. Keep it on the runner's disk and it disappears with the job. Neither gives you a way to ask what actually changed, because neither records anything.

Stow records it. The workspace is a real directory with a durable identity that outlives the process that made it, and a checkpoint is a sealed manifest of what was inside — every path, its size, its mode, its SHA-256.

02

Prepare, work, checkpoint, diff, hand off.

Five verbs, all of them explicit. Nothing is retained implicitly, and nothing leaves the machine unless you ask it to.

stow-s3 workspace prepare declares the inputs 
# task.json — inputs name a source and a destination inside the workspace
{ "version": 1, "root": "/srv/run/ws",
  "inputs": [{ "source": "./report.md", "destination": "report.md" }] }

$ stow-s3 workspace prepare --manifest task.json
{
  "workspace_id": "ws_84845327e66e83fd",
  "root": "/srv/run/ws",
  "bucket": "stow-workspace-a2231176545311e8",
  "seeded_objects": 1,
  "base_identity": "sha256:964580fcc01265bd…",
  "capabilities": { "backend": "workspace", "max_bytes": 67108864, "max_objects": 10000,
                   "persistent": true, "multipart": true },
  "authority": ["object.read", "object.write", "object.delete", "object.list", "bucket.*", "environment.reset"]
}

The capability block is reported, not promised. Limits and the authority actually granted come back from the server, so a caller reads them rather than assuming them.

stow-s3 workspace diff what the agent changed 
$ stow-s3 workspace diff --from cp_5fac28a6… --to cp_b19c02e4… --registry-dir ./registry
{
  "changes": [
    {
      "path": "report.md", "kind": "changed",

                "sha256": "8568539c13e1dd98…" },

    }

}

A checkpoint travels

  • Files with modes and SHA-256 hashes
  • Logical buckets and object bytes, portably
  • Content type, user metadata, checksums
  • Declared Git provenance, detached
  • Relative working directory

It does not

  • Private .stow state or credentials
  • Your .git or process memory
  • Anything outside the workspace root
  • Effects outside the filesystem
  • Original object version IDs, guaranteed

A checkpoint is not a permission and not a handle. Handing one over does not grant authority: adoption on the far side is a separate decision, by you, about a directory that now belongs to someone else's run.

S3 where you need it.

Storage is selectable per server: memory for throwaway work, filesystem when data has to survive a restart, and run-through when you want a local S3 in front of an upstream bucket you already have. Defaults are 64 MiB and 10,000 objects, reported in the capability block rather than assumed.

Implemented

  • Buckets: create, list, inspect, delete
  • Objects: put, get, head, copy, delete
  • List with prefixes and pagination
  • Range reads
  • Conditional reads and writes
  • MD5, CRC32, CRC32C, SHA-1, SHA-256
  • Multipart uploads
  • Presigned requests
  • SigV4 authentication
  • Scoped access control per operation

Not implemented

  • Object versioning, and versionId is refused
  • ACLs and bucket policies
  • Lifecycle rules and replication
  • Event notifications, tagging, object lock
  • S3 Select
  • KMS-backed encryption

And the limit worth stating plainly: Stow is not a sandbox. It owns a data directory and an S3 API. It does not isolate arbitrary host processes or their network access, and workspace quotas do not hard-limit writes made straight to the filesystem.

Portable because you decided where it goes.

Not because the runner happened to survive, and not because somebody else's bucket happened to keep it. It is free, it is Apache 2.0, and it is one binary. If it breaks, the issue tracker is the fastest way to tell me.
