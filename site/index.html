01 / CI & integration tests

CI is waiting for a storage container.

A test needs to upload a file. First comes Docker setup, an image pull, service startup and a readiness check. Storage adds another service to start, wait for and tear down on the runner.

With Stow Start the packaged native process from your test. The helper handles readiness and cleanup, with a private bucket for each run. No Docker daemon or storage image required.

An agent edits files on a disposable machine. Before that machine goes away, you need to keep the result, inspect what changed, and move saved work to the next host.

With Stow Prepare a task workspace, checkpoint its files, and export a verified archive before cleanup.

CI & integration testsStart S3 from the test. Skip the Docker setup.

The problem Your CI job needs an S3 endpoint before the tests can start. Pulling a storage image, starting its container, wiring the service, waiting for readiness and cleaning it up all add setup work and startup time to the job.

With Stow Use the native binary included with the npm package. withStow starts a loopback endpoint, waits for readiness and cleans up after the callback. Your test uses a real S3 client without a Docker daemon, storage image or CI service definition.

A native process, a ready client, automatic cleanup

The session starts the packaged server on loopback and waits until it is ready. Store an artifact, read it back, and let the callback clean up—even if it throws. Each run also gets a private bucket and generated credentials, so parallel tests can use the same object keys. Pass s3 and bucket to your application's storage code.

TypeScript creates the bucket automatically. Python creates it explicitly. Go uses an embedded object runtime without an HTTP server.

Setup: install the TypeScript package from npm with its native binary. Python uses a source checkout. A session is a separate server process, isolated from your cloud environment and bounded by its own quota.

Reject a stale update

A conditional write compares the ETag you read with the object's current ETag and refuses the write if they differ, so two writers cannot clobber one another. A create-only write is refused when the store cannot confirm the object is absent, so it never replaces bytes it could not read.

Agent workspacesKeep the result when the checkout is gone.

The problem An agent's changes live in a task directory, alongside inputs and generated files. Deleting the checkout or replacing the host can discard the files needed to review or continue the work.

With Stow Declare the inputs, prepare a workspace, pause its writers and capture a checkpoint. Export the saved files before disposal. Your host still owns agent execution, permissions and restart.

1. Declare the task checkout

In a fresh directory, save this as task.json. Git fetches the URL first; Stow resolves the local clone's HEAD and prepares a separate detached checkout.

task.jsonJSON
{
  "version": 1,
  "root": "./tasks/task-42",
  "working_directory": "repo",
  "repositories": [{
    "source": "./source-repo",
    "destination": "repo",
    "ref": "HEAD"
  }],
  "ttl_seconds": 3600,
  "registry_dir": "./stow-registry"
}

Your host starts the agent in the returned working directory and controls its process permissions. Expiry requires a collection call; it does not delete the workspace automatically. Git input limits and cleanup.

2. Fetch and prepare

Replace the URL and branch. These commands use Git, Stow, and jq to read the returned IDs.

prepare.shShell
git clone --depth 1 --branch main \
  https://github.com/your-org/your-repo.git source-repo
mkdir -p tasks
stow-s3 workspace prepare --manifest task.json > task-ready.json
jq -r .working_directory task-ready.json
# Run your agent in that directory.

3. Save the result, then dispose

Stop the agent's writers, then checkpoint and export before cleanup. The archive is kept; the task directory and its internal checkpoints are removed.

finish.shShell
WORKSPACE_ID=$(jq -r .workspace_id task-ready.json)
stow-s3 workspace checkpoint --id "$WORKSPACE_ID" \
  --registry-dir ./stow-registry > checkpoint.json
CHECKPOINT_ID=$(jq -r .checkpoint_id checkpoint.json)
stow-s3 workspace export --checkpoint-id "$CHECKPOINT_ID" \
  --registry-dir ./stow-registry --output result.tar.gz
stow-s3 workspace destroy --id "$WORKSPACE_ID" \
  --registry-dir ./stow-registry

        Local read cacheRead retained files when upstream is unavailable.
        

          
The problem A local tool needs objects from S3 to do its work. Without a retained copy, an upstream outage or a disconnected host turns a read into a blocked task.

          
With Stow Fetch through a filesystem cache or prewarm specific keys before going offline. Cached objects remain available within the cache's limits and TTL; an uncached key still needs upstream.

        

        

          

            
1. Start the disk cache

            
Install the native server, configure upstream credentials in your environment, and replace the endpoint and bucket below. These demo credentials are for the local endpoint.

            

              
cache.shShell

              
STOW_ENDPOINT=https://s3.example.com \
STOW_BUCKET=assets \
stow-s3 serve --mode run-through \
  --backend filesystem \
  --port 9000 \
  --access-key demo-local \
  --secret-key demo-local-secret \
  --data-dir ./stow-data \
  --cache-dir ./stow-cache \
  --cache-max-bytes 2147483648 \
  --cache-ttl 24h

            

            
The disk layer retains up to 2 GiB with a 24-hour TTL. Stow revalidates cached objects online. Offline reads require retained bytes. Upstream credentials and offline setup.

          

          

            
2. Put a small memory cache in front

            
Install @aws-sdk/client-s3 and lru-cache. Save this as read-assets.mjs and run it with Node. Replace the image key with an object already in your upstream bucket.

            

              
read-assets.mjsJavaScript

              
import { LRUCache } from "lru-cache";
import { S3Client, CreateBucketCommand,
  GetObjectCommand } from "@aws-sdk/client-s3";

const memory = new LRUCache({
  maxSize: 32 * 1024 * 1024,
  ttl: 30_000,
  sizeCalculation: bytes => Math.max(1, bytes.byteLength),
});
const s3 = new S3Client({
  endpoint: "http://127.0.0.1:9000",
  region: "us-east-1", forcePathStyle: true,
  credentials: {
    accessKeyId: "demo-local",
    secretAccessKey: "demo-local-secret",
  },
});
try {
  await s3.send(new CreateBucketCommand({ Bucket: "assets" }));
  async function readAsset(key) {
    const hit = memory.get(key);
    if (hit) return hit;
    const result = await s3.send(new GetObjectCommand({
      Bucket: "assets", Key: key,
    }));
    if (!result.Body) throw new Error("Missing object body");
    const bytes = await result.Body.transformToByteArray();
    memory.set(key, bytes);
    return bytes;
  }
  await readAsset("images/cover-v1.png"); // disk → S3 on miss
  await readAsset("images/cover-v1.png"); // memory hit
} finally {
  s3.destroy();
}

            

            
The app owns the memory cache. Its byte budget counts retained payloads, not total process memory. Use versioned keys or invalidate memory entries when content changes.
